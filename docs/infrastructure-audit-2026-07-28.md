## 1. Деплой и фактическая топология

**Развёрнуты две разные системы.** В репозитории (`deploy/`) описан один прод, на сервере работает совсем другой.

| Аспект | Репозиторий (`deploy/…`) — целевая архитектура | Сервер по факту |
|---|---|---|
| Реверс-прокси / TLS | Caddy 2.8, строгий CSP + HSTS, блок `/api/v1/metrics` | **nginx-proxy-manager** со своими Let's Encrypt-сертификатами |
| Оркестрация | `compose.production.yml`, ~20 сервисов | Такого compose-проекта нет |
| Backend API | контейнер `api-gateway:4100` в сети compose | приходит на `127.0.0.1:4101` через **реверс-SSH-туннель с удалённого хоста** |
| Мост до API | — | ручной `socat` (`supportcom-api-bridge.service`): `172.17.0.1:4101 → 127.0.0.1:4101` |
| ~18 воркеров (outbox, telegram-polling, sla-timer, report-*, knowledge-*, clamav…) | описаны в compose | не запущен ни один |
| БД / Redis / S3 | внешние managed | на сервере нет (внешние — с хоста не проверить) |
| systemd-окружение | `/opt/support-communication`, юзер `support-communication`, `/etc/support-communication/production.env` | ничего из этого не создано |
| Домен | `APP_DOMAIN` (в примере `support.example.com`) | боевой `supportcom.ru`, не зафиксирован в репо |

**Фактический поток трафика:**
```
supportcom.ru ─→ 95.31.2.38 (NAT на Pi) ─→ nginx-proxy-manager :443
        ├─ supportcom.ru  → socat 4101 → 127.0.0.1:4101 → ssh -R туннель → удалённый backend
        └─ ea.supportcom.ru → etl-etl-analytics-1:3000  (отдельный проект, ClickHouse@Yandex Cloud)
```

**Последствия расхождения:**
- Строгие security-заголовки из `deploy/caddy/Caddyfile` (CSP, HSTS, блок метрик) **в бою не действуют** — работают дефолты nginx-proxy-manager.
- Развёрнутая схема (npm + socat + внешний туннель) **не воспроизводима из репозитория** и нигде в нём не описана.
- Есть незакоммиченные правки рабочего дерева (`docker-compose.yml`, `docker/nginx.conf`, интеграции backend, `src/*`) — прод/локалка расходятся с origin.

**Инцидент доступности:** на момент аудита `supportcom.ru` возвращал 502 минимум с 21 июля — реверс-туннель до `4101` был опущен, socat проксировал в `Connection refused`. socat с `Restart=always` перезапускает только сам себя; **реальный API поднять на этом Pi нечем** — он приходит извне.

## 2. Защита сервера от внешних воздействий

### 🔴 Critical

- **C1. Веб-терминал `omv_cterm` под root на `0.0.0.0:5000`, доступен из WAN.** Flask+SocketIO плагин OpenMediaVault, работает от root, вход по PAM-паролю, fail2ban нет. Уже прощупывается ботами (~17 внешних соединений в момент снимка). В связке с беспарольным sudo у `pi` и его членством в группе `cterm` подбор одного пароля = удалённый root. **Снять порт 5000 с проброса на роутере в первую очередь.**
- **C2. SSH: включены пароли И вход root, порт 22 в WAN, fail2ban отсутствует.** Активный брутфорс: 2942 попытки с одного IP за неделю, ~8000+ неудач с 63 IP за 18 дней (в `btmp` суммарно 232 065). **Пробития нет** — все успешные входы только по ключу с вашего IP. Но парольный путь открыт и ничем не тормозится.

### 🟠 High

- **H1. Хостового firewall нет вообще** (iptables INPUT ACCEPT без правил, ufw не установлен). Вся защита снаружи — только NAT роутера. Docker/podman публикуют порты в обход хостовых правил (нужны правила `DOCKER-USER`).
- **H2. `/opt/etl/.env` доступен на чтение всем (`644`)** — там живые `CLICKHOUSE_PASSWORD`, `AUTH_ADMIN_PASSWORD`, `AUTH_SESSION_SECRET` ETL-дашборда. Любой локальный процесс их прочитает. → `chmod 600` + ротация раскрытых кредов.
- **H3. Админки на `0.0.0.0`:** nginx-proxy-manager admin API (`:81`, отвечает без аутентификации, светит версию 2.15.1) и вебморда OMV (`:8080`). Если роутер их форвардит — торчат в мир. → привязать к LAN/loopback, проверить, что учётка админа NPM не дефолтная.
- **H4. Беспарольный sudo у `pi`** (`pi ALL=(ALL) NOPASSWD: ALL`) + членство в группах `root`(gid 0) и `cterm`. Множитель ущерба для C1/C2: любой захват `pi` = мгновенный root. → убрать NOPASSWD.

### 🟡 Medium

- **M1.** ETL-дашборд опубликован напрямую на `0.0.0.0:3000` по HTTP в обход TLS (тот же логин, что на `ea.supportcom.ru`). → публиковать только на `127.0.0.1:3000`.
- **M2.** `wsdd` (`:5357`) имеет внешнее соединение (Linode-IP) — служба обнаружения должна жить только в LAN.
- **M3.** `PermitRootLogin yes` — ставить `no`/`prohibit-password`.

### Веб-атаки (все отбиты, 404/502)
Веерное сканирование `/.env`, `/dump.sql`, `/wp-config.php`, `/terraform.tfstate`, `/actuator/health`; попытка залить ботнет **Mozi** через NETGEAR `setup.cgi` RCE; зонды `/SDK/webLanguage`. Файлов нет, ничего не пробито.

### ✅ В порядке
SMB закрыт правильно (`bind interfaces only`, только LAN `192.168.1.67:139/445`, host-ACL). TLS валиден: `supportcom.ru` до 19.10.2026, `ea.supportcom.ru` до 25.09.2026, автопродление NPM работает. `unattended-upgrades` активны, security-обновлений в очереди 0. Бэкдор-туннелей не найдено (IP `67.205.183.148` — это атакующий, а не свой канал).

## 7. Уязвимости в коде (SAST)

`npm audit --omit=dev` — **0 уязвимостей** (корень и backend).

### 🟠 High
- **Broken Access Control: `GET /api/v1/integrations/workspace` без аутентификации и без тенант-изоляции.** `integration.controller.ts:15` — нет `@UseGuards`/`@RequireTenantOperatorPermission` (у соседних эндпоинтов есть), глобального гварда нет. - **Глобальное доверие CA Минцифры РФ** через `NODE_EXTRA_CA_CERTS` (`docker-compose.yml:33,497`). Сертификаты подлинные (Минцифры/Ростелеком), **TLS-проверка НЕ отключена** (нигде в репо нет `rejectUnauthorized:false`/`NODE_TLS_REJECT_UNAUTHORIZED=0`).
