# Content brief: чат поддержки для сайта

Статус: Gate A, первая волна  
URL: `/website-support-chat/`  
Владелец продукта: не назначен; перед production требуется ручное подтверждение claims из evidence-блока.

## Роль страницы

Solution landing между главной и технической документацией. Она отвечает на коммерческий вопрос «как организовать чат поддержки на сайте», а `/docs/` сохраняет ownership технических схем API и SDK.

## ICP и job-to-be-done

- руководитель поддержки: принимать обращения сайта в общей очереди и контролировать обработку;
- владелец небольшой команды: запустить дополнительный канал без отдельного кабинета для операторов;
- интегратор/администратор: подключить Web SDK к разрешённому домену и проверить обмен сообщениями.

Job: «Когда посетитель пишет на сайте, я хочу, чтобы обращение попало в рабочую очередь, оператор ответил из общего интерфейса, а клиент получил ответ и мог оценить диалог».

## Search intent

- primary intent: `solution`;
- funnel: MOFU/BOFU;
- representative query: `чат поддержки для сайта`;
- supporting: `чат для сайта`, `онлайн чат для сайта`, `виджет чата для сайта`, `web sdk чат`, `чат с оператором на сайте`.

SERP ожидает feature landing с понятным подключением, возможностями виджета, интеграциями, ценой/CTA и FAQ. Comparison pages тоже присутствуют, поэтому страница должна давать достаточно конкретики для выбора.

## Unique value proposition

Не отдельный чат-кабинет, а входной канал в Support Communication: сообщения и файлы от посетителя, presence и приглашения, ответы оператора, маршрутизация и CSAT в одном операционном сценарии.

## Подтверждённые функции

- SDK endpoints identify/messages/uploads/presence/ratings/polling: `backend/apps/api-gateway/src/integrations/public-api.controller.ts:64–419`;
- проактивные приглашения через presence: тот же controller, строки 98–142;
- рабочая маршрутизация/назначение/SLA: `backend/apps/api-gateway/src/routing/routing.controller.ts:14–106`;
- customer ratings и quality workspace: `backend/apps/api-gateway/src/quality/quality.controller.ts:15–118`;
- публичный API/SDK уже описан в `/docs/`.

## Обязательные ограничения

- нужны SDK key, разрешённый домен и настройка интеграции;
- не обещать установку «в одну строку», запуск «за минуты» или совместимость с любой CMS без проверки;
- не обещать 24/7, измеренное повышение конверсии, скорость ответа или uptime;
- не использовать вымышленные отзывы, логотипы, проценты или клиентские данные.

## Структура

1. Hero: задача, аудитория, primary CTA «Начать бесплатно», secondary «Посмотреть API».
2. «Не ещё одно окно»: признаки разрозненного процесса.
3. Workflow `посетитель → Web SDK → очередь → оператор → ответ → оценка`.
4. Возможности канала: сообщения/файлы, presence, приглашения, polling ответов, CSAT.
5. Подключение: домен, SDK key, настройка и тест — без обещания фиксированного времени.
6. Работа команды: маршрутизация, SLA и качество как связанные, но не гарантированные результаты.
7. FAQ.
8. Финальный CTA и ссылки на `/pricing/`, `/docs/`, `/support-sla/`.

## Демонстрационный визуал

Оригинальная HTML/CSS-схема без реальных данных: посетитель «Анна, демонстрационный диалог» отправляет сообщение и файл; карточка проходит через очередь к оператору и завершается запросом оценки. У схемы текстовая подпись «Демонстрационный сценарий».

## CTA и аналитика

- primary: registration/onboarding, goal `registration_start`;
- secondary: `/docs/` и goal `docs_view` при route view документации;
- route view: `website_chat_view` один раз после consent;
- KPI после накопления данных: non-brand impressions, CTR, organic landings, registration starts, demo form opens/submits; без количественного target до baseline day-28.

## Competitive gap

В SERP много страниц, продающих собственно виджет и список функций. Страница Support Communication должна показать канал как часть рабочего процесса поддержки и честно описать технические prerequisites.
